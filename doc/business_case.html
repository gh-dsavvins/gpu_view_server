Moving view sorting to the GPU

Business case and proof of concept · gpu_view_server

Our view server pushes a live, individually filtered and sorted viewport of the order book to every connected screen every 300 ms. As views and orders grow, re-ranking the table for every view becomes the bottleneck. This is a memory-bandwidth problem, and current GPUs have several times the memory bandwidth of the largest servers. A working proof of concept shows the GPU engine producing identical results to our CPU approach, faster.

1. The problem

Every view has its own filter and sort order. On each tick the server must work out which orders fall into each client's visible window (for example rows 1,000–1,050 of "open orders by notional, descending") and push them.

Fills change a handful of orders per tick, which could be handled incrementally. But market data moves constantly, and the columns users sort and filter on most (notional at market, distance to market, P&L) are derived from market data. They change for nearly every open order on every tick. Incremental sorted indexes stop helping: each tick is effectively a fresh ranking of the whole table, once per distinct view, and pivot aggregates must be recalculated too.

2. Why CPUs run out of headroom

Ranking a view means reading the filter and sort columns of every row. The work is simple; the limit is how fast memory can be read. Rough sizing for the target load (estimates, not measurements):

Running the views in parallel does not change the arithmetic: the total bytes read per tick are the same, and a single large ranking already saturates memory.

3. Proposed design

  1. The order table lives permanently in GPU memory. Each tick uploads only the changed cells (fills, new orders) and the latest instrument prices: kilobytes to a few megabytes.
  2. Market-data-derived columns are recalculated once per tick for all orders, in under a millisecond.
  3. Each view is ranked with a radix select: only the visible window is found, never a full sort. Views are processed in batches so the GPU stays busy.
  4. Pivot aggregates are accumulated in the same pass over the data.
  5. Only the visible rows and pivot cells come back to the CPU (≈ 24 MB per tick for 1,000 views).
  6. The CPU keeps what it is good at: client connections, WebSocket/protobuf encoding, per-client diffs.
Two GPUs, each holding a full copy of the table, split the views between them. If one fails, the other serves all views. No special interconnect is needed.

4. Proof of concept

Built and measured on a 2013 Mac Pro running Debian: 12-core Xeon and two AMD FirePro D700 GPUs (2013-era, ≈ 264 GB/s each). Old hardware on purpose: if a decade-old GPU beats the same machine's CPU, a current one will beat current CPUs by a wider margin.

  • Server (C++, Vulkan compute): simulated order book with realistic fills, cancels and market data; CPU engine using every core; GPU engine using both GPUs; WebSocket + protobuf API.
  • Client (TypeScript, browser, same stack as our current app): live sorted views, header-click sorting, scrolling, pivots, and a live CPU/GPU switch with timing.
  • Correctness: both engines produce bit-identical results (row order, totals, pivot sums), checked on every benchmark tick and optionally every live tick.

5. Risks and mitigations

RiskMitigation
GPU memory capacity15M orders × 60 columns × 4 bytes ≈ 3.6 GB, well within 48–96 GB cards.
Hardware failureTwo GPUs, each with a full copy; the CPU engine stays as a fallback path.
Precision32-bit values on both paths; the PoC verifies identical results tick by tick.
Vendor lock-inPoC uses Vulkan (any vendor). A production build may use CUDA for its libraries.
Team skillsThe GPU part is a small, isolated engine (≈ 10 kernels) behind the same interface as the CPU engine.
OperationsGPU drivers and monitoring become part of the deployment; to be covered in the pilot.

6. Recommendation

  1. Approve a pilot: one server with two current GPUs, fed by a replay of real order and market data.
  2. Success criteria: the target load (15M orders, 1,000 views, 300 ms) with at least 2× headroom, results identical to the current engine, failover tested.
  3. Decide on production rollout after the pilot.
